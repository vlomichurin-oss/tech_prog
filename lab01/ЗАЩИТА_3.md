# Лаба 3 — шпаргалка к защите

Запуск (из корня репозитория):

    python -m labs.lab3.demo   # демонстрация всех паттернов
    python -m labs.lab3.main   # сама игра

## 1. Что такое шаблоны проектирования, зачем, классификация

Шаблон проектирования — проверенное, повторяемое решение типичной задачи проектирования в ООП. Это не готовый код, а «рецепт», который реализуется под конкретную ситуацию. Зачем: не изобретать велосипед, делать код гибким и расширяемым, иметь общий словарь между разработчиками («тут строитель» — и всем понятно).

Классификация (GoF):
- порождающие — как создавать объекты (Одиночка, Строитель, Прототип, Фабричный метод, Абстрактная фабрика);
- структурные — как собирать объекты/классы в более крупные структуры (Адаптер, Декоратор, Фасад…);
- поведенческие — как объекты взаимодействуют и распределяют обязанности (Стратегия, Наблюдатель, Шаблонный метод…).

## 2. Порождающие паттерны

Отвечают за создание объектов: прячут логику инстанцирования и отвязывают код от конкретных классов. Решают задачи: создать объект, не зная его точного класса; гарантировать единственный экземпляр; пошагово собрать сложный объект с проверкой; получать объекты копированием готовых образцов.

## 3. Одиночка (Singleton) — `core/dice.py`, класс `Dice`

Что делает: гарантирует один экземпляр класса и даёт к нему глобальную точку доступа.

Реализация: в Python нет приватных конструкторов, поэтому перехватываем `__new__`: экземпляр хранится в `Dice._instance`, создаётся лениво при первом `Dice()`, дальше возвращается тот же объект. В демо: `Dice() is Dice()` → `True`.

Зачем у нас: один генератор случайности на всю игру → один сид (`reseed`) воспроизводит весь бой (`explore(hero, 7)` всегда даёт одинаковый результат).

Плюсы: точно один экземпляр; доступ откуда угодно, не надо таскать через конструкторы; ленивое создание.
Минусы: глобальное состояние; скрытые зависимости (по конструктору `Bow` не видно, что он зависит от `Dice`); трудно подменить в тестах; наша реализация не потокобезопасна (два потока могут одновременно создать два объекта — нужна блокировка или создание сразу).
Когда применять: только когда объект действительно должен быть единственным (общий ресурс: генератор, конфиг, логгер, пул соединений).

## 4. Строитель (Builder) — `hero/hero.py`, класс `Hero.Builder`

Что делает: отделяет пошаговую сборку сложного объекта от самого объекта.

Реализация: вложенный класс `Hero.Builder`; методы `set_name`, `set_hero_class`, `set_starter_kit`, `set_level`, `set_gold` возвращают `self` → цепочка вызовов; необязательные поля (уровень=1, золото=50) имеют значения по умолчанию в строителе; все проверки в `build()` — если что-то не так, герой не создаётся (`ValueError`). Конструктор `Hero(builder)` берёт значения из строителя; закрыть его в Python нельзя — действует договорённость «только через строителя». В демо: создаём Артура, а героя без имени и без класса `build()` не пропускает.

Чем лучше конструктора с кучей параметров: нет «телескопических конструкторов» (по варианту на каждую комбинацию необязательных параметров); не перепутаешь параметры одного типа (уровень и золото — оба int), по цепочке видно, что чему присваивается; валидация объекта целиком в одном месте; можно собирать по шагам (снаряжение приходит из фабрики отдельным шагом).

Минусы: больше кода, поля объявляются дважды (в герое и в строителе); для 2–3 полей избыточен.
Когда применять: много полей, часть необязательна; объект собирается по шагам и нужно проверить его целиком перед созданием.

## 5. Прототип (Prototype) — `item/item.py` (`Item.copy`), `item/item_catalog.py`

Что делает: создаёт новые объекты копированием уже существующих, не завязываясь на их конкретный класс.

Реализация: у `Item` есть метод `copy()`: `copy.copy(self)` создаёт объект того же класса (меч, лук, посох, броня) с теми же полями, после чего список `_enchantments` заменяется новым. `ItemCatalog` хранит шаблоны и в `create(code)` вызывает `prototype.copy()`, не зная, какой там класс. Наружу отдаются только копии — шаблон испортить нельзя. В демо: две копии железного меча, на вторую накладываем «Огненное» — первая и новая копия шаблона остаются без зачарования.

Плюсы: создание без привязки к конкретным классам; вместо класса на каждый предмет — настроенный объект-шаблон; копия создаётся самим объектом, который знает все свои (в т.ч. закрытые) поля.
Минусы: копирование надо поддерживать — забыли скопировать новое изменяемое поле → копия и оригинал снова делят данные; сложно копировать объекты с циклическими ссылками.
Когда применять: объекты отличаются в основном данными, а не поведением, и их удобно получать из заранее настроенных образцов.

## 6. Глубокое и поверхностное копирование

Поверхностное (`copy.copy`) — создаётся новый объект, но его поля ссылаются на те же вложенные объекты, что и у оригинала. Глубокое (`copy.deepcopy`) — рекурсивно копируются все вложенные объекты.

Что важно при поверхностном: изменяемые вложенные объекты окажутся общими. У нас без замены списка зачарование, наложенное на копию, появилось бы и на шаблоне в каталоге. Поэтому изменяемый список копируем (`list(self._enchantments)`), а неизменяемые `Enchantment` (`frozen=True`) можно делить — их никто не поменяет. Полный `deepcopy` здесь — лишняя работа.

## 7. Фабричный метод (Factory Method) — `world/location.py`, метод `_create_enemy`

Что делает: базовый класс объявляет метод создания объекта, а какой именно объект создать — решают подклассы.

Реализация: абстрактный `Location._create_enemy() -> Enemy`; общий алгоритм `explore()` (восстановить здоровье → создать врага → бой → награда/штраф) написан один раз в базовом классе и вызывает фабричный метод. `Forest` возвращает `Goblin`, `Crypt` — `Skeleton`, `DragonLair` — `Dragon`. В демо: одна и та же `explore` в лесу даёт гоблина, в склепе — скелета. (`explore` заодно пример Шаблонного метода.)

Плюсы: `Location` не зависит от конкретных врагов; новая локация = новый подкласс, код экспедиции не меняется (открыт для расширения, закрыт для изменения).
Минусы: на каждый вид продукта нужен свой подкласс создателя (10 врагов → 10 классов локаций).
Когда применять: у класса есть общий алгоритм, а создаваемый в нём объект должен меняться в наследниках.

## 8. Абстрактная фабрика (Abstract Factory) — `kit/`

Что делает: создаёт семейства связанных объектов, не привязываясь к их конкретным классам.

Реализация: абстрактный `StarterKitFactory` с двумя порождающими методами `create_weapon()` и `create_armor()`; реализации `WarriorKitFactory` (меч + кольчуга), `RangerKitFactory` (лук + кожаная броня), `MageKitFactory` (посох + роба). `HeroClass` знает свою фабрику, строитель героя получает набор через `set_starter_kit`. В демо выводятся три разных семейства.

Плюсы: согласованность семейства (воину не достанется роба); клиент работает с абстракциями; новый класс героя = новая фабрика + строка в `HeroClass`.
Минусы: добавить новый вид продукта (например, зелье) тяжело — меняется интерфейс фабрики и все реализации.
Когда применять: состав семейства устоялся, а сами семейства добавляются часто.

## 9. Фабричный метод vs Абстрактная фабрика

- Фабричный метод — это метод самого класса, переопределяемый в наследниках (наследование); создаёт один продукт; вызывается самим классом внутри его бизнес-логики (`explore`), снаружи его никто не дёргает.
- Абстрактная фабрика — отдельный объект, который передают тому, кому он нужен (композиция); создаёт целое семейство продуктов (несколько методов); её методы вызывает внешний код (строитель героя).
